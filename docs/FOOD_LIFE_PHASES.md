# 森林之家「食」与日常生活：阶段施工总纲

> 状态：2026-11-05 目标与阶段规划；供后续 agent 接续施工。此文件**不规定具体实现方式**，也不代替仍在并行形成的「住」类施工文档。两边文档完成后再统一宿主、触发和场景呈现，避免抢先重复建设。

## 定位与目前判断

这是《森林之家》的**「食—日常节律」专题**四阶段，不等同于全项目的 M0–M2 里程碑，也不意味着要把游戏变成厨房经营或生存模拟。

玩家住在温带混交林的营地里，白天自由探索、采集、适度采伐，傍晚回家准备食物，坐一会儿读森林故事，然后主动选择夜游或睡到日出。**不吃饭不会饿死，也不阻止散步、采菌、拾枝；想在次日砍成熟树、搬大原木等做重活，则需要事先吃一顿。** 玩家的主要目的仍然是经营森林、修缮家园和享受林间生活；食物使这些活动形成自然的每日收束，而不是制造一套每天必须刷的需求条。

本规划以 `main` 的 `e2e04a59`（2026-11-05）为核对基线：食物 PR #18、晚间生活 PR #20 已随合批 PR #21 进入主线，HUD 整改 PR #22 也已合并；当时主线 CI 通过。另有树杈与树皮 PR #23、东岸与收运 PR #24 尚在并行施工，后续 agent 应以开工时的主线和实际合并状态重新核对，不能据此文件覆盖其他分支。发布状态与代码合并状态分别判断。

## P1｜基础闭环：工程阶段已完成

**目标已经达成：** 一条有真实物品去向与时间后果的最小链路可以运行，不再只有锅、灶台和词条构想。

| 已具备的基础 | 目前边界 |
| --- | --- |
| 森林鲜菌、行商整袋干粮、拆包后的豆/米/燕麦/黑面包/调味品 | 商品数量与到访频率仍是候选经济参数 |
| 晾制鲜菌成干菌；在已有火塘的汤锅里用菌类和一种谷物煮正餐 | 只有少量基础食物，不是完整菜系或加工工艺树 |
| 成品真实入库和消费；用餐记录次日劳动资格；不吃仍可进行轻活 | 只在已接入的重体力动作上生效，不追求营养、饥饿、疲劳或每日体力条 |
| 18:00 沙漏自动停靠；玩家可续开沙漏夜游；回帐篷后可结束一天并于 06:00 醒来 | 夜间活动、生活动作的节奏感尚待体验层调校 |
| 篝火边坐读、简化坐姿和木碗、10 则本地短故事及起床过场 | 属于初版可用表现，不代表完整的用餐动作、丰富故事内容或精修美术 |
| 统一库存、时间、世界存档及 HUD 查看—走近—操作 | 已通过自动检查与 HUD 专项浏览器验证；食物至次日的整段游玩仍应独立体验验收 |

**阶段判定：P1 可以关闭，不再拿它当一个继续无限追加功能的施工包。** 不足之处归入 P2–P4；不要为了补旧蘑菇、木墩或私人原型历史存档，重新开启与当前目标无关的工程。

## P2｜把一日生活做成真正舒服的游戏体验（下一阶段，优先）

**目的：** 让玩家自然理解并愿意反复体验「白天活动 → 傍晚收工 → 准备/享用食物 → 随意看几页故事 → 夜游或休息 → 第二天继续」，而不是依次点击几个功能测试按钮。

重点不是增加系统数量，而是让现有行为在同一个营地和适当的镜头距离下连贯呈现：

- **时间的主动权清楚。** 沙漏加速不会跳过 18:00；玩家到傍晚可以继续做饭、用餐、读书、干其他事，或恢复夜间时间。睡觉是主动结束一天，恰好到下一次日出，不变成额外的等待、随机签到或多天快进。检查首日从 14:00 开始与以后 06:00 起床的体验是否合理，不擅自把首日改成完整的一天。
- **用餐是一段实际可理解的行为。** 食物拿得出、吃得掉，有明确但克制的角色/器具表现；吃饱与否对第二天工作的后果清楚可感。无需另设食物放大镜、精细锅内特写或烹饪小游戏。普通无词条的饭也应该值得做。
- **阅读是一种自愿的休息。** 坐下、拿碗、翻几页、合上书、起身这几个动作保持自然；允许跳过阅读直接收工，也允许不吃饭而读故事。故事与森林环境协调，不让大段说明侵入平常 HUD。现有十则故事先作为可玩内容，是否大规模扩库留给 P4。
- **正常镜头看得见，界面不添乱。** 顺着已合并的 HUD 规范：常驻信息少；远处先走近，近处再操作；镜头只适度靠近，不因一只碗增加一张技术面板。桌面和手机都保持清晰的操作动线。
- **不强制一日一清单。** 不吃、不阅读、入夜继续探险都有效；不因为错过某次晚饭让玩家无法采集维持生活。不要让日历、采伐许可、行商来访和沙漏分别拥有冲突的“第二天”定义。

**可见验收：** 玩家能完整玩过有工作的一天和没吃晚饭的一天；前者次日可做重活，后者可继续轻活；12× 沙漏不会越过晚饭；夜探与结束一天互不冲突；角色、镜头、食物、故事和按钮之间没有令人困惑的跳转。优先用实际游戏画面和一段连续游玩判断，而不只看单个按钮或测试通过。

**不做：** 扩大菜谱、铺满厨房用具、重做行商交易、复杂 NPC AI、批量制作奇趣词条、公开发行级兼容工程。

## P3｜少量食物路线与材料供给的整合（暂缓；与行商、住类一并启动）

**目的：** 让玩家有限的森林收获与行商补给能够自然搭配；库存每样东西并不一样多，吃几天后会有材料先用完，从而改变下一顿做什么。**菜品由食材性质、份量和已有器具决定，而不是先收集几百张菜谱。**

- **来源两端明确。** 森林提供菌类等合理的当地可采物；行商提供豆、谷物、黑面包、少量盐与辛香料和必要五金。行商仍以一袋可用的混合补给为主要体验，不要求玩家从零碎货架逐一挑选。烹饪鼓励森林材料与干货 A+B 组合，但黑面包等基础口粮可以直接吃。
- **只建立少数食品系列。** 菌菇汤、野菜或谷物杂烩、简单烤食、干粮/热饮等是可选择的方向，不把系列名称误当成必须全部制作的任务。食材可以替换，额外材料只改变适当的外观、风味、饱足程度或少量后续表现；合格的正餐都能承担基础“吃饱”作用。
- **加工沿已有物件扩展。** 先复用晾晒、汤锅、烤网、简单储存；烟熏、盐渍、发酵、橡实去涩/研磨等曾评审过的方向作为可选后续，不因为一个工艺就增加一件孤立的设备。没有农田种植或经营餐厅的计划。
- **统一核对贸易与生活节律。** 行商目前存在低频到访、每次粮袋数量和信用限制；要核对这些条件与每日重体力劳动需要食物的关系，确保缺粮时仍能继续轻度活动，并存在合理的补给机会。不能把经济缺口归因于“玩家应该天天等商人”。
- **与「住」类协同。** 灶台/炉火结构、架设位置、器具制作与升级由两边文档统一，食物系统负责原料加工、成品、消费与食物相关效果。不为食物单独复制火源、余温、自动添柴和炉旁皮影。

**可见验收：** 在有限食材条件下，玩家可以用至少两种来源组合出不同但同属少数系列的日常食物；某样干货先耗尽后仍能合理改用手头材料；所有产物有真实去向，不凭空增发；不会因此多出第二套厨房或商品系统。

此阶段**等行商 NPC 与「住」类文档一并对齐后再开工**。不能抢先固定来访周期、五金采购细目、灶台附件归属或复杂加工的整套设计。

## P4｜奇趣词条、共餐关系与林间叙事（后续内容阶段）

**目的：** 让少量真实常用器具在偶尔触发时显出性格和惊喜，但不让营地变成不停表演的杂技厨房。奇趣可以顽皮、温柔，也可以神秘，不必提供正经数值奖励。

前期 F01–F100 已口头筛选：**接受 50、不要 26、修改/待合并 24**。这些是概念评审结果，**不是已做成的 50 个可执行词条**；“修改”不自动视为接受，“不要”不自动复活。正式施工前按载体、实际触发与正常镜头可见性收拢：基础用途归器具本体，特殊升级归图纸/升级，奇趣额外效果才归词条。

优先从已接受的、共享表现方式较多的方向中挑代表项，而不是按编号逐条清仓。例如 F71 鸳鸯斗气、F73 面饼打哈欠、F74 木勺指挥家、F77 陶坛跳舞、F95 木杯幻影鹿角、F100 饭后谢幕。它们应在正常营地/用餐视角明显可辨、出现频率克制、不干扰玩家操作，也不得要求制作精细锅内特写。被修改的 F80「尚飨」仍需在神秘性上另行确认，不能把巨大木勺当成已批准的祭坛表现。

当 NPC 系统具备相应行为后，再接 F10 留客半碗、F20 灶边搭手、F30 先尝为敬、F40 尝味改袋等；**谁愿意来、什么时候来、是否接受邀请属于 NPC 系统**，食物只提供适当的环境、物件和交互机会。故事可以逐渐扩展成预生成的本地文库；实时 API 仅作为以后短篇、受世界设定和长度约束的可选叙事，不应成为普通吃饭的网络依赖。

**可见验收：** 少量代表词条在真实场景中各有辨认度，三种趣味气质不冲突；不同器具能共享必要的视觉能力；没装词条的普通器具仍完整可用；NPC、食物、器具的拥有者和触发事件讲得通，互动不会任意扣物或在无人场景中空演。

## 给接手 agent 的交付约定

1. **紧接着做 P2，不把 P3/P4 的想法顺手塞进 P2。** 每阶段交付应是玩家能够连续体验的一段生活，不是一组没有接线的模块、素材或调试控件。
2. **先对齐最新 main 与并行 PR。** 此文档只提供目标和验收；允许 agent 根据已有实现决定具体施工方案，不能为了实现某条候选效果重构不相关系统。与仍在形成的「住」类文件发生分歧时保留待对齐项，不单方冻结。
3. **界面与叙事尊重操作心智模型。** 场景先行、查看—走近—操作、常驻 HUD 极简；玩家看的文字是游戏语言，不是开发说明。角色动作/锅碗效果在正常视角明显可见。
4. **保留核心不变量。** 一套世界日历和库存、一处资源结算；日常生活自愿、重活有进食前提但没有饥饿死亡；自由探索/森林经营/木作仍是游戏中心。当前为私人原型开发，不把旧档迁移或历史试稿验收强塞成每阶段门槛。
5. **对齐已确定的词条评审意见。** 可用例子供施工选型，不以本阶段划分自动批准 F 项修改候选或重选否定项。每阶段结束只记录目标达成、实际可见效果、仍待另一线程确认的交界点；不要把计划写成已完成。

**阶段顺序：P1 已完成基础工程 → P2 生活体验收敛（先做）→ P3 食材/行商/住类整合（等并行设计）→ P4 奇趣与共餐叙事（在可用器具和 NPC 基础上）**。P3、P4 的具体实施窗口与拆分可以由后续 agent 调整，但不得改变已确定的游戏定位。
