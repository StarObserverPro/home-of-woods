# 物品扩展与存档兼容方案

日期：2026-10-30。状态：物品身份、品质堆叠、库存切片兼容读写和旧会话适配已实现；现有世界持久存档已接入，具体品种、加工执行和建筑玩法后续接入。设计范围见 [原 scope](scopes/item-data-compatibility-review.md)，实现范围见 [当前 scope](scopes/item-stack-compatibility.md)，状态与提交所有者遵循 [RENDERING](RENDERING.md)。

新增菌种、木种和加工品，通常应当只增加内容定义；只有保存结构或既有物品含义发生变化，才需要迁移玩家数据。为此，物品身份必须脱离显示名称、目录顺序与当前内容表大小，品质必须进入库存的堆叠身份，已经产生的加工结果必须独立于最新配方存在。

## 当前数据的扩展边界

当前 [items](../src/content/items.ts) 以稳定字符串登记 `mushroom`、`branch`、`wood` 等物品，并明确材料、形态、默认品质与 active/planned/retired 状态。[qualities](../src/content/qualities.ts) 登记未分级、普通和精品；[inventory](../src/domain/inventory.ts) 以 `itemId + qualityId → quantity` 保存稀疏数量，新增目录项不会自动扩大每份库存。`schemaVersion` 管结构，`revision` 每次事务递增，不随库存切片持久化。

[warehouse-view](../src/domain/warehouse-view.ts) 从实际堆叠解析品质与已知/未知条目，同时保留当前活跃物品的零数量展示。原木已归统一库存，采伐与采集都先生成库存候选再提交；`ForestryState` 只持有额度、树木和采伐动作。[inventory-persistence](../src/domain/inventory-persistence.ts) 实现库存切片 JSON 往返，[inventory-session](../src/app/inventory-session.ts) 在场景进入前适配旧会话。当前完整世界持久存档见 [WORLD_SAVE](WORLD_SAVE.md)；[processing](../src/content/processing.ts) 仍只登记加工候选，尚无制作提交。

## 物品身份与品质堆叠

物品定义识别“是什么材料、处于什么加工形态”；品质属于这批库存的等级。同一物品可以拥有不同品质，不必为每个等级复制整份目录定义。下面的名称和 ID 只说明结构，不构成正式菌种清单或加工配比。

| itemId 示例 | 定义中的材料与形态 | 库存中的 qualityId 示例 |
| --- | --- | --- |
| `fungus.pine.fresh` | 松蘑、鲜品 | `ordinary` 或 `fine` |
| `fungus.pine.dried` | 松蘑、干制品 | `ordinary` 或 `fine` |
| `fungus.bolete.fresh` | 牛肝菌、鲜品 | `ordinary` 或 `fine` |
| `timber.pine.log` | 松木、原木 | `ordinary` 或 `fine` |
| `timber.pine.board` | 松木、板材 | `ordinary` 或 `fine` |
| 现有 `mushroom`、`wood` | 未细分的兼容物品 | `ungraded`，表示原数据没有等级信息 |

ID 是不透明的稳定键；业务读取定义中的 `materialId`、`formId`、类别和用途，不能通过拆分 ID 字符串推断规则。同一 ID 的实体含义不能改写，退出新产出时保留兼容定义；修正旧 ID 使用显式别名或迁移，不能删除后把旧数量映射到一个“差不多”的新品种。

当前库存切片保存的形态为：

```ts
type InventoryStack = {
  itemId: string;
  qualityId: string;
  quantity: number;
};

type InventorySaveV1 = {
  schemaVersion: 1;
  stacks: InventoryStack[];
};
```

同一库存内，只有 `itemId + qualityId` 完全相同的数量可以合并；内部查询键使用无歧义的规范编码，不能使用中文名称、数组位置或简单拼接。拆分、合并与消费都引用这个身份组合。数量使用非负安全整数，零数量可以省略；不保存每个未拥有目录项的零值，也不逐朵蘑菇、逐根木头建立实体。

品质 ID 独立登记，不把 `fine` 的目录序号当成品质值。配方的最低品质使用明确的等级关系；`ungraded` 不自动满足普通或精品要求。后续真有耐久、独立外观或单件改造时，再增加相应的实例结构；当前不加入任意 JSON 属性包。

树种与资源来源是产出条件，具体产物由内容定义显式指定。以后给某种树下的资源池登记某种蘑菇，或为某树种登记某类原木，不需要改变库存格式；宿主代次与资源池仍由原有稳定身份管理，加载物品目录不重抽来源、不补满库存。

## 目录更新与格式升级分开

| 变化 | 兼容处理 |
| --- | --- |
| 增加菌种、木种、加工形态或品质定义 | 增加目录记录；旧库存保持原样，无全档迁移与自动补发。 |
| 调整名称、图标、排序或显示分类 | 更新展示定义，保持 ID 和玩家数量。 |
| 停产、隐藏旧物品 | 保留旧定义及必要兼容用途；停止新产出。 |
| 真正改变某物品含义、单位或保存结构 | 新 ID 或显式格式迁移；记录转换与守恒关系。 |
| 调整配方配比或品质规则 | 新配方版本；只影响之后启动的加工。 |

存档总 `schemaVersion` 管全档结构，库存切片的 `schemaVersion` 管堆叠结构；目录修订号可以用于诊断，不能要求读档时与最新目录完全一致。当前库存已使用 `revision`，只用于候选状态的过期校验。配方版本则识别结算规则，不能替代存档版本。

读档要区分两类未知：

- **目录未知**：保存结构已支持，物品或品质 ID 暂时找不到。原记录及数量进入隔离库存，仓库显示“未识别物品/品质”和原 ID；禁止加工、交易、自动合并转换。只有确认全记录可无损往返、所有相关引用均能保留时，其他已知内容才继续正常存档；恢复定义后可重新识别。
- **结构未知或数据损坏**：未来格式、未知结构字段、非法数量、冲突身份或无法理解的跨切片引用。保留原始数据并保护整档写入，不用空库存覆盖。显示安全投影不等于取得写回资格。

目录未知项的库存切片无损往返与仓库占位已实现，业务事务拒绝使用未知物品/品质。当前完整存档同时校验相关切片的引用；库存加载成功不能单独解除全档保护。水晶花园当前仍对未知物品 ID 进入保护，两项目的兼容策略有所不同。

## 旧泛品与原木余额迁移

旧 `mushroom` 数量不足以反推松蘑或牛肝菌；旧 `wood` 总量也不足以还原每根木料的树种和品质。保留它们为“未分类蘑菇”“未分类原木”，品质记为未分级。兼容配方可明确接受旧泛品，要求具体菌种、木种或品质的配方则排除它们。不能为了清理旧 ID 把未知事实补成新品种或精品。

当前尚未发布持久存档，无需为不存在的历史版本建立空迁移链。第一次接入堆叠库存时，新存档直接采用目标格式；若需要导入既有会话或之后确有旧档，再提供有实际输入样本的一次性适配。

原木已改由统一库存持有；旧会话适配整笔转移 `ForestryState.wood` 的余额，并同时移除旧余额字段。采伐结算、仓库查询与数量入口已统一；旧余额仅供兼容读取，不再成为第二个可消费来源。林业额度账本继续记录采伐许可和已用/预留额度，与木料库存分工不变。迁移前后的存量及未完成动作都须对账，不能在两边各保留一份木头。

## 深加工的输入与结果

配方可以声明某类材料、形态和品质条件，以免每加一种木材就复制整套业务代码；可用材料集合和输出映射必须由定义明确授权，不能仅凭一个泛化的“蘑菇”“木材”标签，让所有未来物品自动参与所有配方。

执行前，把条件解析为具体的 `itemId + qualityId + quantity` 投入，并绑定库存修订号；同一份数量不能同时满足两个输入条件。用户确认的材料或确定性选料规则形成候选，应用层同时验证扣料、产物、设施及幂等动作，再一次提交。默认选料不得暗中消耗玩家保留的精品。

加工形态变化产生相应物品 ID；树种/材料身份由明确输出映射保留，品质变化遵循配方规则与成本。结构木守恒需要统一计量单位和各形态的结构木等价量，检查全部投入与全部产出，允许合理损耗，不能凭枝料增加结构木。当前注册校验只要求“有结构木输出时至少有结构木输入”，不足以阻止一份原木加大量枝料换出任意多结构木；必须在加工执行开放前补成定量约束，配比仍待设计。

已结算加工记录保存动作 ID、配方 ID/版本、实际投入、实际产出及品质；完成记录不按最新配方重算。耗时加工还要保存已预留材料和启动时冻结的结果/规则，读档后按已定义策略继续，或整笔取消退回原投入，不能丢弃旧任务或重复领取。

库存只保存当前数量和必要单件状态。加工记录不把每一层祖先记录递归复制进新产物；需要追溯时用独立收据与引用，历史明细设保留策略。幂等信息可以按已验证的动作序列边界压缩，不能随清理展示历史一起删除，导致旧命令再次发奖。

## 实现顺序与验收

品质堆叠、旧泛品定义、未知目录保留和库存加载结果已实现，仓库、采集与采伐已消费同一库存身份。首个完整持久存档落地时，全档仍只有 app 一个写入者，迁移先生成候选并验证所有切片和引用，成功后一次提交；失败保留原始存档及上一份有效数据。

加工执行开放时，再接入材料选择、配方版本、定量守恒和耗时任务恢复；无需提前实现在线经济、扩展包平台或完整交易系统。

完整实现按以下场景验收；本轮库存/会话部分已由行为测试及 JSON 往返覆盖，加工和完整世界读档部分保留为后续条件：

1. 目录增项、重排、改显示名以后，旧库存身份和正数数量不变；新增目录不会补发物品。
2. 同种普通与精品分别计数，拆分/合并守恒，选料条件重叠不会重复花费同一份材料。
3. 旧泛品不被猜测重分类；原木余额转移一次，重复迁移不增加库存，也不刷新额度。
4. 未知物品/品质保持可见且不可消费；无损保存后重新加载定义，原数量恢复识别。未来结构与非法数值保护原档。
5. 已完成加工跨配方升级保持结果；未完成任务的预留、继续或退款无重复发放，结构木等价量守恒。
6. 安全整理后可正常保存，下次读档不反复进入保护；所有新字段经过真实写入器的 JSON 往返，而非只测试内存对象。
7. 库存、树木代次、资源池、额度和动作记录跨切片校验；读档、卸载重入与目录升级均不刷新采集来源。

本轮实际检查与边界见 [物品兼容证据](../evidence/item-stack-compatibility/README.md)。`tests/item-compatibility.test.ts` 检查品质、未知目录、旧会话转移、保护、整笔失败与库存 JSON 往返；当前世界存读档已验证；加工恢复及建筑切片仍待后续功能接入。旧仓库截图与回执保留其原始版本，不作为本轮实现证明。
