# 营地邻居：来访、人格、记忆与 AI 合同

设计基线：2026-11-19。首批只增加一位住在山另一侧、需要走一段路才到营地的邻居；现有行商继续拥有自己的交易、货单和到访规则。本文件维护邻居系统的分层、行为与 AI 交接约定。当前代码和检查范围见 [本轮 scope](scopes/neighbour-visitors.md)，原有来访基础见 [行商](MERCHANT.md)，营地设施与普通用途见 [营地生活接入](CAMP_LIFE_INTEGRATION.md)。

本轮没有可用的模型 API 凭据。人格、记忆、来访和有限输入处理可以在本地工作；模型输入输出合同与实际模型调用分别记录。未配置的模型服务、未接线的动作或未完成的画面检查，都不能写成已经可用。

本地 runtime、统一存档、场景与 UI 入口已完成接线。构建与已登记的定向行为检查通过，桌面及手机实机画面尚未验证；本轮 Chromium 启动受到环境的 socket 权限限制。当前输入回应采用有限本地规则，API 尚未连接。

## 1. 玩家会遇到的一位邻居

这位邻居偶尔来串门，能招呼、看看营地、闲逛、交谈，并在主人忙碌时做自己的事情。他有固定的外形与生活背景，对木作、林间见闻和营地生活有个人偏好；一次来访只准备一个主要目的及少量可替代活动。

他可以想尝一碗汤、看看新做的凳子，或者帮一点忙，但想做与能够执行分别处理。营地没有成品食物、座位、相应工序或动作支持时，他会看一看、说明缺什么，随后换个活动或离开。不会通过一句台词补造食物、家具、舞蹈动作或完成品。

首批人物叫阿榆，身份为 `ridge-neighbour`，温和寡言，来串门时也有自己的安排。人物资料引用既有 `visitor` 模型；场景适配器配短发、布帽、帆布背心、补丁工裤、靴子和背包，以衣着轮廓和配色与行商区别。复用资源不等于沿用行商的玩法身份。名字、性格、外观色彩和来访参数集中配置；后续增加人物时复用这些合同，不按每个人复制一套主循环、库存或保存器。外观的实际可读性以实机画面检查为准。

## 2. 分层与每人的逻辑目录

| 层 | 保存或处理什么 | 变化方式 |
| --- | --- | --- |
| 外观 | 既有角色模型、骨架、衣着与挂件预设、动作映射 | 资源管理器按外观引用加载；不混入记忆文字 |
| 人格 | 身份、背景、熟悉的事情、稳定偏好、表达习惯 | 作者配置；普通记忆整理不重写人格 |
| 主观记忆 | 重要经历的梗概、仍记得的细节、置信度、最近对话要点、对承诺的回忆 | 由真实交互记录、提醒和周期整理更新 |
| 承诺事实 | 双方明确达成的约定、对象、真实履行或取消状态 | 游戏事件提交；与是否记得分别保存 |
| 本次来访 | 来意、进入与离开、停留截止时间、当前计划、接待状态 | 同一世界时钟和本地状态机推进 |
| 本次会话 | 本次来访读取的人格与可回忆内容、当前可选活动、随后发生的少量增量 | 入场时建立，事件发生时补充，离场后结束 |
| 执行与表现 | 寻路、站位、碰撞、角色移动、动画、道具使用 | 现有本地规则与唯一场景循环；不等待模型逐帧决定 |

代码中的人物资料归 `src/content/npcs/ridge-neighbour/`，共享规则归 `src/domain/npc-memory.ts`、`npc-dialogue.ts`、`npc-visit.ts`，来访参数归 `src/content/npc-visit.ts`。动态记录以 NPC ID 组织在同一世界存档中；“每人一个文件夹”首先表示资料边界，不要求浏览器在每一步动作时重写多个物理 JSON 文件。

若以后提供人物档案导出，可以把一个 NPC 的人格引用、记忆、承诺和当前状态导出为同一目录。导出便利性不改变现有唯一保存所有者，也不让源代码目录成为运行时玩家记忆的写入位置。

## 3. 记忆保存重要内容，不保存行动流水账

适合进入长期记录的内容包括：上次讨论的主要话题、一次共餐或帮助、见过的重要营地变化、未完的对话、明确约定。每帧坐标、上次绕过哪棵树、每次看向哪里、普通路点与无后果的重复寒暄不进入长期记忆。

当前一条 `NpcMemoryCard` 保存以下字段：

| 字段 | 作用 |
| --- | --- |
| `id`、`kind`、`topic` | 事件身份、交谈/共同活动/承诺/观察类别及主题；事件去重另用有限 `processedEventIds` |
| `gist` | 不含精确数量、日期和完整措辞的梗概，例如“和主人约过再看看营地的木作” |
| `details` | 可遗忘的细节，每条有稳定 ID、文本和可选不确定标记；至多四条 |
| `importance` | 1–3 级保留优先级；高重要程度仍可以逐渐遗忘 |
| `day`、`lastRecalledDay` | 原事件日期与真实提醒日期；读取档案不会改写后者 |
| `clarity`、`confidence` | 清楚/模糊/碎片/遗忘，以及人物对内容有多确定 |

`gist` 当前不会被模型自由改写，因此细节必须放进 `details`。如果把“下周二送三根木头”完整写进梗概，删除细节后仍会泄漏精确回忆，这属于主机写入错误。主机还应明确记录“玩家说过什么”和“实际发生什么”的区别；第一批用事件类别、梗概及带引语的细节表达来源，尚未加入独立的来源枚举。

每人当前最多 16 条重要记忆、12 条承诺事实、两轮最近对话和 64 个已处理事件 ID；最近对话只保留三个游戏日内的内容。这些是首批可调参数，不是日后人物数量或模型上下文的永久限制。真实承诺通过 `memoryId` 关联主观条目，但关联不赋予模型读取事实账本的权限。

仅仅载入存档、建立请求或序列化数据不算复习，不能借此刷新记忆年龄。最近对话只保留有限回合与要点；长期记录不靠无限增长的完整聊天记录维持。

### 承诺事实与主观回忆

假设双方确实约定“下次来帮忙看看门边的凳子”。游戏需要知道约定是否已经完成，否则重复对话可能重复结算；邻居却可以逐渐只记得“好像答应来看看一件木作”。

因此，事实账本与模型可读的回忆分开：

- 事实记录只保存已确认的约定与履行状态，不被 AI 压缩改写。
- 人物决策读取主观回忆的投影。已经模糊或忘记的细节不通过隐藏事实账本重新补全。
- NPC 忘记约定，可能导致他没有主动提出、记错无经济后果的小细节，或需要玩家提醒；不会改写已经交付的物品，也不会让已经完成的约定重新发奖。
- 玩家说“你答应送我一百根木头”只是新输入。它可以成为“玩家这样说过”的记录，不能直接变成确实存在的旧约定。
- 提醒可以恢复相关回忆的显著性；重新确认或更改承诺仍通过明确的游戏交互提交。

## 4. 周期整理让记忆真正变化

这里采用的是游戏设计规则，不把一条固定衰减曲线宣称为真实人类记忆模型。

当前 app 在 `tick` 中检查三游戏日的整理资格，达到条件时执行一次本地整理；活跃来访和待处理请求也遵守同一资格规则，并以整理期失效阻断旧上下文。每帧检查资格不等于每帧整理或调用模型，普通对话与读取档案也不单独触发整理。未来接入异步语义整理时，可优先安排在离场后或下次入场前；这属于待实现的调度策略。暂停、后台和关闭期间沿用游戏原有时间边界。

一次整理分三步：

1. **本地准备候选。** 根据年龄、重要程度和真实提醒日期决定哪些条目可以淡化，指定允许清晰度、可保留的细节 ID 和作者提供的有限误记选项。
2. **模型提出整理结果。** 输入人物当下仍可回忆的内容与整理范围，输出清晰度、保留细节 ID，以及可选的一个误记选项。当前合同保留已有梗概，不接受自由重写原文、合并条目或恢复被删细节。未来若开放更自然的语义压缩，需要另加受约束的摘要合同。
3. **本地验证并提交。** 检查 NPC、记忆版本、主机请求日期、条目 ID、允许变化与长度上限；拒绝新增不存在的约定、提升不被允许的精确度、改写已结算结果。提交成功后写回同一份世界状态。

没有模型服务时，本地规则仍可减少细节和置信度，并从已配置的无结算影响的误记选项中作确定性选择。当前每三个游戏日达到一次整理资格；不同重要程度的模糊、碎片和遗忘年龄如下，均从真实事件或提醒算起。

| 重要程度 | 开始模糊 | 只剩梗概 | 不再进入可回忆投影 |
| --- | --- | --- | --- |
| 1 | 3 日 | 9 日 | 24 日 |
| 2 | 6 日 | 18 日 | 42 日 |
| 3 | 12 日 | 30 日 | 90 日 |

模糊时至多保留一条细节，碎片时没有细节，遗忘时整条不进入人物上下文。置信度上限依次为 1、0.65、0.3、0。当前可运行的是这些规则及模型提案的校验入口，尚未验证模型实际产生的整理质量。

### 模糊、遗忘与误记的区别

| 状态 | 人物可以怎样表现 | 规则边界 |
| --- | --- | --- |
| 清楚 | 主动提起具体共同经历 | 内容来自已保存且仍可回忆的细节 |
| 模糊 | “上回好像是下雨那天。” | 减少时间、对象或措辞精度；表达保留不确定性 |
| 遗忘 | 没有主动想起；被提醒后才可能建立新的联想 | 请求中不再暗藏完整原文让模型自行恢复 |
| 有限误记 | 对无结算影响的小细节给出不确定的错误印象 | 只在显式允许的细节类别内变化；不能编造资产、履约或奖励 |

有限误记必须从细节的 `alternatives` 中选择，不能接受任意生成的新事实；替换后不把原细节藏在模型可读字段里。没有配置选项的条目只模糊或遗忘。人物稳定身份、基本世界观与当前真实能力不作为随机遗忘对象。

整理任务带原记忆 `revision`，主机同时验证任务日与当前游戏日。等待模型时若玩家已经提醒过他或发生新互动，旧结果不能覆盖新记忆。会话用 `memoryEpoch` 对应 `consolidatedThroughDay`，使整理后旧上下文失效；普通新增事件通过增量进入会话，不需要因为每次记忆版本变化都重建。活跃会话若仍携带整理前的完整细节，必须结束或重建，否则文件虽写成“忘记”，旧模型上下文仍会使他完美回忆。新会话只保留当前主观记忆，不能把全部旧聊天重新塞回去。

例如主机已经允许一条承诺回忆淡化时，模型可以提交以下提案。这里的版本与日期仅作格式示例，实际必须原样对应主机请求；空的 `keepDetailIds` 表示留下梗概而不保留具体约定细节，不代表取消约定。

```json
{
  "schemaVersion": 1,
  "npcId": "ridge-neighbour",
  "sourceRevision": 17,
  "atDay": 18,
  "changes": [{
    "memoryId": "ridge-neighbour:visit:1:promise",
    "clarity": "faded",
    "keepDetailIds": []
  }]
}
```

## 5. 每趟只建立一次上下文，随后按事件继续

一次来访开始时读取人物档案，形成一个有界会话：人格、当前可回忆内容、此次来意和营地提供的活动。随后本地执行这次短计划。走到下一个路点、等待和播放动作不重新读取人物档案，也不触发模型。

以下变化可以形成增量：玩家实际说了一句话、活动完成或失败、设施变得不可用、双方确认各自活动、出现新的重要互动。增量附带事件 ID 与状态版本。新的信息会影响这次会话，但不会每次重复整个世界快照。

一次计划失效时先使用明确的本地替代活动。例如原本想坐着歇脚，发现没有合适位置，可以说明缺少位置，转去已有的观察点。当前每趟来访至多接受一次模型短计划，后续活动失败由本地消耗候选和改选；以后只有出现值得重新判断的情况才考虑开放有限重规划。每一步路径被挡住都不需要调用语言模型。

一次来访计划只需类似下面的结构。活动 ID 来自这次主机提供的能力表；这段计划不保证有座位，执行第一项时发现条件不足就自然转向后面的活动。计划无需输出路径坐标、关节动作或每秒台词。

```json
{
  "visitId": "ridge-neighbour:visit:3",
  "expectedRevision": 0,
  "wishes": ["rest-seat", "observe-workbench", "warm-fire"]
}
```

### 应用会话与供应商上下文是两件事

本项目保证的是应用按一次来访建立档案上下文、后续发送增量的组织方式。供应商是否缓存前缀、是否保留会话、不同模型间是否能直接继续，应由将来的适配器按其公开 API 处理。

OpenAI 的 `previous_response_id` 可以延续响应链，但官方明确说明链中的旧输入仍按输入 token 计费；不能将一个会话 ID 理解成以后只为新一句话付费。[官方会话文档](https://developers.openai.com/api/docs/guides/conversation-state)

Claude 的提示缓存复用匹配前缀，读取和写入缓存仍有 token 使用记录；缓存减少重复处理的成本与延迟，不会使长档案没有代价。短档案、有限历史和少调用仍是本项目的主要控制手段。[官方缓存文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

本地的会话 ID 只标识游戏会话；未接入前不将它描述为云端已经创建的持续 Agent。模型供应商切换或角色分流时，传递需要的有界上下文投影；不能假设不同模型共享隐藏记忆。

## 6. 模型按任务使用，普通动作在本地执行

| 任务角色 | 何时需要 | 输入与输出规模 | 无模型时 |
| --- | --- | --- | --- |
| 输入理解 | 自由输入存在歧义、需要判断话题与意图时 | 当前一句话、少量近文、允许意图；返回类别和至多一个意图 | 处理已支持的明确表达；不确定时澄清或不接话 |
| 来访规划 | 当前每次来访至多接受一次；后续重要变化的重规划另行开放 | 一次来意、当前能力与少量主观记忆；返回最多四个活动 ID | 使用本地来访规则和可用活动 |
| 角色表达 | 玩家真正与他交谈、发生值得回应的事件时 | 当前事件、有限对话上下文；返回短台词或不说话 | 选择符合场景的预写回应 |
| 记忆整理 | 达到整理条件时 | 一批可变动记忆与允许操作；返回结构化变更提案 | 本地有界衰减，不伪装成 AI 已整理 |

这些是可配置的任务角色，可以共用一个轻量模型，也可以只给表达使用较强模型。第一阶段不需要四个常驻 Agent。没有要说的话、没有新判断时不发请求；安静走一走可以完全由本地短计划执行。

配置应使用 `planner`、`dialogue`、`memory_consolidator` 等职责名，再由连接器映射到已核实可用的供应商模型 ID。讨论中的模型档位称呼不直接当作有效 API 名称。当前没有配置在线模型、没有执行付费调用，也没有建立新的密钥或云端账户。

## 7. 自由输入、世界观和可执行动作

输入先区分是不是对这个人物说的、是否属于世界内可以理解的内容，再判断是在闲聊、提出动作、作出约定还是提醒旧事。人物允许沉默、没听懂和转回当前话题，不要求接住每句话。

| 输入情况 | 人物反应 | 执行边界 |
| --- | --- | --- |
| 世界内的一般聊天 | 一两句符合人物经验的话，或继续当前动作 | 不凭聊天生成任务、道具与数值 |
| 指代不清 | “你说门口那个，还是火边这个？” | 明确目标前不执行 |
| 世界外或明显不搭边 | 简短表示没听懂，或看向眼前的东西转回话题 | 不把外部话题扩成通用问答 |
| 能理解但动作未实现 | 表示不会、做不了，或提出已有替代活动 | 只提供当前能力表里的动作 |
| 动作已有、现场条件不足 | 看看所需位置，说清缺的东西，暂缓或换事 | 不补造设施、材料或动画 |
| 要求改身份、改规则、读隐藏记录 | 保持原人物身份，简短不接话或转回场景 | 玩家输入只是人物听到的话，不升级为系统配置 |

例如“我唱歌，你跳舞”属于世界内可理解的请求。若没有舞蹈能力，人物可以说自己不会，或只听一会儿；以后能力表有舞蹈与可用位置时，同一类请求再进入真实动作。“别跳舞，看看椅子”必须识别否定和实际目标，不能因为出现“跳舞”两个字就启动或拒绝舞蹈。

本地过滤只是第一层，不能靠一张关键词黑名单保证任意中文语义理解。无法可靠识别的表达采用短澄清或不理解回应；未来模型理解结果也要经过相同的能力和现场校验。

### 输出合同

当前对话模型合同允许 `reply`、`unclear`、`redirect`、`action` 四类结果；每次至多提出一个动作，文本最多 120 字符。没有需要说的话时，主机可以不请求模型，访客继续自己的活动。输出须带来访 ID、轮次、记忆整理期和有限意图/目标引用；不允许返回可执行脚本、任意资产路径或自由拼接的游戏命令。

应用依次验证：NPC/来访仍然有效、输出属于本次允许范围、目标仍存在、所需能力已实现、现场条件仍成立，再把合法意图交给现有领域操作。失败结果返回场景，人物可以自然改变主意。

例如玩家说“去火边暖一会儿吧”，模型只需提出以下动作意图。主机重新判断火塘活动能否执行，再生成接受或条件不足的回应；模型无需自己宣布已经完成取暖。

```json
{
  "visitId": "ridge-neighbour:visit:3",
  "turn": 2,
  "memoryEpoch": 3,
  "kind": "action",
  "intent": "warm-fire",
  "targetId": "neighbour:fire"
}
```

模型提出工具调用、应用执行工具，是现有 API 支持的分工；结构约束可以防止字段类型与工具名称不匹配，但现场资格仍需游戏检查。[工具调用官方文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) · [严格输入约束](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use)

涉及承诺与真实结果时，台词不能在检查之前宣布“已经做好”。表达层只拿到已接受的计划或实际执行结果。响应晚到、访客已经离开或玩家已经换目标时，过期结果不再补说、不再补做。

## 8. 时间：日历推进与人物速度分开

继续复用唯一 `GameState.time`。访客停留截止时间保存为世界时间；运动与短动作消费同一主循环提供的未乘沙漏倍率的 `dt`。这两个时间用途明确，但不建立第二套游戏日历。

| 在场状态 | 0× / 1× | 4× / 12× | 停留与动作 |
| --- | --- | --- | --- |
| 正在接待、交谈或共同活动 | 可用，具体暂停服从当前统一界面规则 | 拒绝并说明先结束互动 | 日历按当前有效速度走；人物动作保持普通速度 |
| 已明确“你先转转”，双方各自活动 | 可用 | 可用 | 世界截止时间照常消耗，客人在较短现实时间内进入离场 |
| 主人在全屏木工中专注操作 | 服从木工宿主的正常时间规则 | 工作模式允许时可用 | 客人只做自己的活动，没得到回应可以到期离开 |
| 全局暂停、页面隐藏或关闭 | 暂停 | 不推进 | 不在后台继续走路或整理记忆 |

例如还剩四个游戏小时，切到 4× 后，剩余的现实等待时间约为原来的四分之一；人物不跑成四倍速。独自活动时期限到达便开始告别和离场，走完离场路径仍按普通移动速度，不为了赶截止时间在眼前瞬移。若到期时正在交谈或共同动作，先标记需要离开，结束当前互动后告别。原有 18:00 停靠仍有优先权，不被访客系统绕过。已经加速时如果新客人到达，主机也应立即重新判断并切回 1×，不能只校验玩家点击加速按钮的那一刻。

全屏木工的“主人专注”是明确的宿主状态，不由模型猜测。邻居不会打开对话、抢焦点或强行加入制作；他能在允许的营地位置看一看、休息，或等不到回应后离开。普通仓库整理、全局暂停与木工专注应分开传递，避免误把所有打开面板都视为可以继续跑访客时间。

当前独立木作组件是否已经接入主线，要以实际宿主为准；提供 `hostFocused` 合同不等于所有并行木作入口已接线。

### 睡眠与留宿

普通在场访客不能被一次睡眠跳转悄悄越过。先完成当前互动并告别；已经进入 `leaving` 时可以按原规则睡眠，睡眠淡出会结束这次已经说清的离场。日常可见的离场仍按原速走路，不在镜头前瞬移。以后若有可用寝具、留宿行为及双方确认，才允许共同度过夜晚的跳转；“留宿”不只是给状态字段设一个布尔值。

首批未开放的过夜能力保持不可用。不能用 AI 一句“我住下了”绕过床位、空间与实际玩法前置。

## 9. 来访与宿主的交接

本地来访模块对外提供创建、校验、推进、互动和快照。宿主提供当前世界时间、原速 `dt`、主人是否在营地/专注、可用活动点与路径规划。模块不直接读取 UI，也不创建渲染循环。

约定入口为 `createNpcVisitState`、`tickNpcVisit`、`interactNpcVisit`、`applyNpcVisitPlan`、`npcVisitClockReason`、`npcVisitSleepReason`、`settleNpcVisitForSleep`、`npcVisitSnapshot`、`validateNpcVisitState`。互动意图覆盖招呼、交谈、结束交谈、各自活动、告别和选择已注册活动；实际参数与支持范围以源码类型为准。

当前来访记录为 `version / visitIndex / nextVisitAt / lastDepartedAt / active`。活跃来访将两类状态分开：`phase` 为进入、等待、游逛、交谈、活动、离开；`attention` 为未回应、已接待、明确各自活动、主人专注。它还保存 `startedAt / deadlineAt`、当前路径和站位、有限计划及活动进度；这些运行数据只用于续玩，不进入长期人格记忆。

首批调试参数是：初访在开局 30 世界秒后获得资格；玩家在营地、游戏时间处于 09:00–17:00 且入场路线可用时才出现。每次正常停留四游戏小时，相当于当前日历尺度的 200 世界秒；离场后间隔两个游戏日。角色移动速度为每现实活动秒 2.4 世界单位，受同一地形、道路与碰撞限制。停留期限按资格实际启动时计算，不从失败的寻路尝试开始计时。

`src/scene/neighbour.ts` 仅消费来访状态与主循环传入的普通场景秒数；复用角色模型、服装与动作资源，不调用模型 API、不改变记忆、不提交活动结果。行走依据真实位移，空闲和挥手依据普通场景时间；观察工作台与火塘只调整面向，未实现的坐、吃和跳舞不靠动画假演。外观克隆只替换自身附件的材质引用，资源仍由既有缓存所有者释放。

来访状态、人物记忆和承诺由 app 在真实事件边界衔接。模型输入只消费可见快照；人物表现只消费状态；台词、动画和 API 回调都不成为库存写入者。主线的保存、场景重建、取消与暂停继续由既有 owner 处理。

## 10. 验证重点与后续顺序

本轮针对以下真实风险检查，不为这一个邻居建立发布级 NPC 平台：

- 原速与倍速下移动距离相同，停留期限消耗不同；接待与交谈确实阻止加速。
- 主人专注时客人可以自主活动并离场，不抢全屏木工的输入；全局暂停时全部停止。
- 缺失目标、设施和动作时不假装完成，晚到的模型建议不能操作过期状态。
- 记忆整理改变人物可读的内容；旧承诺事实和已结算物品不变；没有通过旧会话偷偷恢复已遗忘细节。
- 一次来访只有一次基础上下文构建；普通路径推进不产生模型请求；增量与整理分别有大小边界。
- 语句的否定、指代不清、离题与无能力回应可区分；未知输入不被硬猜成有副作用动作。
- 同一邻居的来访、记忆与承诺能够随当前世界保存和恢复；恢复不重发物品或重复产生已完成互动。
- 模型、动作、选中与短界面需要实际画面检查；构建、类型检查和状态机测试不能代替可见验收。

优先把一个邻居的进场、各自活动、招呼、短交流、记忆变化与离场做完整。真实共餐、帮厨、木作协作、舞蹈、留宿及更细外观，分别在相关营地能力具备后加入。后续模型接入重点验证表达质量、语义理解、记忆整理和成本，不改动这套本地事实与执行边界。
