# 行类道具：基础交互、词条效果与局部动态契约

此文档承接独立对话「整理行类词条」关于**先有道具本体，再有词条**、**小范围动态表现**和**系统前置依赖**的共识。词条对话仍负责逐项评审；这里是工程注册与接口，不重新判定 X 项接受/修改/不要，也不把候选效果提前做成已开放玩法。

## 道具和词条必须分别有来处

- **独立 Item**（`ITEM_CATALOG.ownedItems`）负责本体是什么、图纸怎样制作、实例是谁、它现在在哪。旅行伞、帽子、望远镜、口哨、旅行毯、背包在 `src/content/owned-item-definitions.ts` 中仅作为 planned 本体登记，不自动发给玩家。
- **Base action** 是物品正常用途：伞展开/合拢、帽子戴上、望远镜观察、口哨使用、旅行毯铺开。动作应先能独立于词条运行；当前 `src/content/item-behaviors.ts` 仅预留 planned 操作，所需装备位/目标选择/观测系统均尚未开放。
- **Trait effect** 是某个实际实例的词条赋予的附加行为，必须再次确认`traits` 含对应 ID。它既不能替本体发图纸，也不能允许没有本体的独立效果。允许同一物品多词条，但未知/待实现词条只有数据，不偷偷改变数值或动画。
- **Object-local motion** 是呈现层对个别子节点的小动作，不自动等于物理、受力、角色全身动画或经济效果。独立状态转换（伞打开）与连续局部动画（行走时蝴蝶结、毯子尾巴）不能用同一个随机物理效果冒充。
- **World interaction** 需要玩家行动、实际对象和场景条件：触发可以是主动点击、移动事件或环境事件；地图、水路、索道、搬运工具/承重、澡堂等系统尚不存在时，不能使对应操作变成可执行状态。

## 新增的数据分层

| 数据 / 模块 | 责任 | 不负责 |
| --- | --- | --- |
| `content/owned-item-definitions.ts` | 本体身份、开放状态、制作图纸、挂载能力 | 特效执行 |
| `content/item-behaviors.ts` | 操作 ID、ownerDefinitionId、base/trait、触发、目标、允许归属、前置、handlerId、motionProfileId | 玩家动作/材料结算 |
| `domain/item-behaviors.ts` | 校验本体、实例词条、距离/目标类型、环境、所需物品与执行 handler，产生一次性待处理意图 | 绕过近身交互、自动制作或运行不认识的 handler |
| `domain/item-local-motion.ts` | 基于传入实际动画时间的确定性局部角度偏移 | 沙漏倍速、游戏收益、设备运动/受力 |
| `scene/item-local-motion.ts` | 对**单个场景实例根节点**的已命名子节点叠加旋转并在释放时复原 | 创建模型、音效、第二个渲染循环 |
| `domain/item-attachment-contract.ts` | 现有宿主槽位与安装有效性；`itemMountedContexts` 从宿主槽读取环境上下文 | 把词条复制到宿主 |

目前所有新的行类本体、基础 action 和局部动态模板状态均是 `planned`。即使字段正确也不能发出可执行命令；需有 active 本体、active action、匹配实例/词条、前置系统、明确目标、站位以及已注册 handler 才能返回合法动作意图。**目标不能只是一个类型标签**：指向地面需传世界范围内的实际坐标，指向其他道具需传稳定实例 ID，环境触发需传已经确认发生的上下文事件 ID；意图中原样保存经校验的目标，留给后续 handler 做场景、路径和事务复核。未来真正接 UI 时遵循“查看 → 走近或明确选择对象 → 再次检查前置 → 执行动作服务 → 一次结算”的项目流程，绝不能把前置未满足简单解释成灰掉但可远程扣料。

## 极小动态，而不是复制整套物理引擎

`LocalMotionProfile` 每个模板限定 1–2 个子节点、旋转轴、幅度、频率、相位和驱动条件（`time` 或 `movement`）。`sampleItemLocalMotion` 不改变 GameState；`createItemLocalMotionBinding` 在 Three.js 实例上绑定/重置/释放。所有模板未开放，资源和命名锚点需要日后实际建模后接入。

参考「行」类讨论：
- 旅行毯动物形态可以只让尾巴等 1–2 处轻摆，**不加声音**；当前只登记一个 `tail-tip` 运动模板，不生成动物毯模型、不声称 X86 修改方案已经正式实施。
- 旅行背包上的蝴蝶结可随人物移动而局部摆动，两个结翼相反相位；`moving=false` 或减少动态效果时立即回中性位置。这只是 X93 的表现方法示范，背包本体和玩家装备/携带状态仍为 planned。
- 伞顶喷泉、云帽遮阳、镜里奇景、口哨回嘴都需要先做基本伞/帽/望远镜/口哨，再接后置词条。普通道具的基础动作不应要求玩家先抽到这些词条。
- 与 Zipline、扩大地图、长程水域有关的特效保留系统前置；搬运中“搬不回去”的定义、回收和运回路径归现有 carrying/物流机制，不在词条 handler 里捏造额外丢失或速度惩罚。水桶盖和洒水等表现也应等水桶/澡堂系统明确后接入。
- 已拒绝的方案不注册为功能；筛选中属于“修改”的方案也不自动被当作接受。

## 运行时、存档和升级路径

这批不动 `inventory.instances` 的身份和 `ItemLocation`，不改变 `traits` 与稀有度生成，不升级库存/世界规则。Action registry、运动模板、handler 意图都是代码内容；动画相位是可重建的表现缓存，不写入世界存档。动作**真正产生持久效果时**，再由对应业务 handler 负责幂等事务和需要存档的对象状态。

局部动画调用者提供 unscaled active-play 时间；不额外开计时器、不要跟 1×/4×/12× 沙漏乘速，不在后台补模拟。暂停由宿主停止推进入参；减少动态效果直接回到基础姿态。对同一个 GLB 的不同实例应分别绑定各自局部节点，避免污染共享材质/模型。音频不在该局部动画契约中，旅行毯明确不设计声音。

未来新增特殊效果，先补 `ItemActionDefinition(source:'trait',traitId)`、明确原道具与触发对象，并在真实消费端上线前保持 planned。不要为了让未启用词条看起来“生效”，修改物品分类或宿主设施等级。一个特殊视觉可以注册 motion，但真实互动/物理/经济收益需要单独的 handler 或规则，不从动作幅度推导收益。

## 验收边界

`tests/item-behaviors.test.ts` 覆盖 planned 不执行、基础能力和词条能力的门槛、触发/目标/近身/系统/前置物品/handler、未知词条不生效、轻量动态 1–2 锚点上限、两结翼反相、减少动态与停止走路复位、Three.js 绑定复原、安装上下文不复制物品属性。CI 的 TypeScript、测试、构建、证据审计通过，也不代表已经完成旅行伞、旅行毯或背包等真实交互/动画美术验收。
