日期：2026-11-05。用于当前私人单人原型的日常交接，承接 [AGENTS](../AGENTS.md)；不增加发布级审批或独立文档服务。目标是让后续施工能区分完整规划、当前代码、实际验证和交付位置。

## 状态必须带对象和范围

| 状态 | 必要依据 | 不能由它推断什么 |
| --- | --- | --- |
| planned / 候选 | 规划来源、评审意见、真实载体与前置 | 注册字段、参数或模型草案不等于功能可用；修改不等于接受 |
| implemented-local / 本地已实现 | 当前工作树/提交中的实际入口、数据流与普通用途 | 不等于已推送、远端合并、已发布或已通过全部视觉验收 |
| verified-main / 主体已验证 | 明确版本/范围、命令或实际操作、环境/视口及结果 | 自动检查不替代画面；fixture 不证明正常取得；局部样板不代表全阶段 |
| verified-sandbox / 沙盒已验证 | 独立入口、版本、存档命名空间和本次证据 | 回接字节一致也不能自动改写为主体证据 |
| merged-remote / 远端已合并 | 对应 PR 的 merged 状态、合并时间/提交等实际结果 | open PR 的非空 `merge_commit_sha` 可能是测试合并提交，不是 merged 证据 |
| released / 已发布 | 实际发布目标、版本与部署/可访问结果 | 本地 build、开 PR 或合并代码都不等于部署成功 |

同一阶段可以有已实现代表、已验证切片和仍计划中的扩展。以具体目标及覆盖范围记状态，不用接受项数量计算完成率。文档基线日期与核对日期都保留；有后续授权时追加推进映射，不让旧“暂缓”掩盖已获准的有限施工，也不把有限施工改写成全阶段完成。

## 一次同步怎样收口

1. 读当前 README、相关规划/合同及对应源码，核对工作树、main 和相关 PR 的实际 head/state；PR 元数据与原文件使用固定提交定位。
2. 确定谁维护哪个文件。写现有文件前比较读取时的内容摘要；有并行变化就重新读取并按段合并。新文件确认未占用后创建，不整目录覆盖。
3. 按用户授权和实际用途选取要接入的规划内容；完整原文保留来源，选择性合并旧文档的索引，不把远端旧 README 覆盖本地新推进。
4. 当前合同写“现在怎么工作”，进度映射写“原目标做到哪里”，验证只写已经发生的检查。历史段落保留日期并指向现行合同，不为修一处状态重写无关历史。
5. 检查新增/修改的相对链接、评审统计、命名空间、前置与状态是否相互一致，检查差异与末尾空白。文档改动不新增空壳运行时测试或无意义 CI 门禁。
6. 交付列出本次文件、真实结果、未测范围与下一 owner；开 PR、推送、合并、发布按各自当次授权处理。

## 工程检查与本轮分工

既有 workflow 继续承担资产、构建和当前功能的实际回归；精确命令以 [.github/workflows/verify.yml](../.github/workflows/verify.yml) 为准。只在已实现的行为需要保护时加入有意义的现存专项，避免把无关历史回放或发布级兼容工程搬回日常门禁。CI 改动的代码、实际运行与结果分别记录，文档中的建议不视为已经执行。

沙漏实现及其 scope、CI/PR 模板、完整规划和推进映射随本合批实现共同交付；开工核对与本地验收截面保留日期，实际检查结果集中维护在根 [VERIFICATION](../VERIFICATION.md)，GitHub 交付状态见[推进记录](CAMP_LIFE_PROGRESS.md#规划来源与交付状态)及所属 PR / main。后续各模块按文件职责更新，通过状态只引用已经发生的检查。主体、历史沙盒和临时 fixture 的数据库/来源与验证范围继续分别标明。
